## 1. Summary

The `design` plugin is a set of seven prose skills (six of them also exposed as slash commands) and a manifest, built for Cowork and Claude Code, that turn a design request (critique, system audit, handoff, copy, accessibility, research synthesis) into a structured Markdown report. It ships no code, no deterministic check, and no test. Everything it produces is an opinion an LLM writes, shaped by a fixed output template; whether the opinion is correct is left to the human reading it. Its one piece of real infrastructure is the connector model: skills degrade gracefully (prose branches "if connected / else describe it to me") instead of failing when an MCP server like Figma is absent.

Verdict for CGSpec: this plugin is a well-organized prompting layer, not a verification layer. It is useful evidence for how to word skill triggers and how to write a connector-degradation story, but it supplies nothing that could be adopted as a machine-checkable gate. CGSpec's `visual_audit.py`, `journey.py` and the critique rubric already cover the ground this plugin leaves to "the agent's judgment."

## 2. How the plugin is structured

- **Manifest** (`.claude-plugin/plugin.json`): name `design`, version `1.2.0`, one-line description, author `Anthropic`. No dependencies, no scripts, no hooks declared.
- **Skills** are plain `SKILL.md` files under `skills/<name>/`, each with YAML frontmatter: `name`, `description` (the trigger text), and for command-style skills an `argument-hint`. The `description` field is the whole triggering mechanism — for example `design-critique`'s frontmatter says to trigger "with 'review this design', 'critique this mockup', 'what do you think of this screen?', or when sharing a Figma link or screenshot for feedback at any stage." There is no separate router, no classifier, no scoring; matching is left entirely to the host's own skill-selection behaviour reading that description.
- **Commands vs skills**: the README lists the same six capabilities twice — as slash commands (`/critique`, `/design-system`, ...) and as "skills Claude uses automatically when relevant." The skill files themselves are written as command bodies (`## Usage` → `/design-critique $ARGUMENTS`), so in this plugin a "skill" and a "slash command" are the same file.
- **Connectors and graceful degradation** (`CONNECTORS.md`, `.mcp.json`): the plugin never names a specific product in its instructions. It uses placeholders like `~~design tool` or `~~project tracker`, and `CONNECTORS.md` maps each placeholder to the servers actually wired in `.mcp.json` (Figma, Slack, Linear, Asana, Atlassian, Notion, Intercom) plus "other options" the user could swap in (Sketch, Jira, Amplitude, etc.). Every skill ends with an "If Connectors Available" section, e.g. accessibility-review: "If **~~design tool** is connected: Inspect color values, font sizes, and touch targets directly from Figma." When no connector is wired, the skill's main body already works from "a Figma URL, screenshot, or description" — the connector section is pure upside, never a requirement. Two entries in `.mcp.json` (`google calendar`, `gmail`) have an empty `"url": ""`, which the plugin does not explain; `CONNECTORS.md` does not mention either server, so this looks like an unfinished or unused stub, not a documented feature.

## 3. Skill by skill

- **design-critique**: asks for the design plus "context" and an optional "focus," then grades it under five fixed headings (first impression, usability, visual hierarchy, consistency, accessibility) and fills a Markdown table with severity tags (`Critical/Moderate/Minor`) chosen by the model itself. Nothing here is measured; contrast and touch-target numbers are typed in as prose, not computed. Enforcement is 100% prose: the rubric is a checklist for the model to narrate, not a script.
- **accessibility-review**: the most mechanical of the seven — it quotes real WCAG 2.1 AA success criteria (1.4.3 contrast ≥ 4.5:1, 2.5.5 touch target ≥ 44×44px, 2.4.7 visible focus, etc.) and a 5-step "testing approach" ("Automated scan (catches ~30% of issues)", then keyboard-only, screen reader, contrast, 200% zoom). But the skill itself runs none of these checks; it asks the model to fill a contrast table with values it has not measured unless a connector supplies them ("Inspect color values... directly from Figma"). The WCAG numbers are real and quotable; the audit process around them is still narrated by the model.
- **design-system**: three modes (`audit`, `document`, `extend`) over one file, producing a "Score: X/100" and tables of pass/warning/fail icons per component. The score has no defined formula anywhere in the file — it is the model's impression dressed as a number. "Token Coverage" asks the model to report "X instances of hardcoded hex," which again depends entirely on a connector (Figma) or the model reading files; standalone, it is a guess.
- **design-handoff**: produces a spec sheet (tokens, states, breakpoints, edge cases, animation) with the explicit principle "Don't assume — If it's not specified, the developer will guess. Specify everything" and "Use tokens, not values — Reference `spacing-md` not `16px`." This is a genuinely useful authoring discipline, but again enforced only by the model remembering to follow its own template; nothing checks that a value in the output spec actually traces to a real token.
- **research-synthesis**: turns transcripts/surveys into themes, an insight→opportunity table, and segments, with one real methodological rule stated as prose: "Separate observations from interpretations — '5 of 8 users clicked the wrong button' is an observation. 'The button placement is confusing' is an interpretation." Useful as a reviewer discipline; not checkable by a script.
- **user-research**: not a slash command, just a reference skill — a table of methods (interviews, usability tests, surveys, card sorting, diary studies, A/B tests) with sample sizes and durations, an interview-guide outline, and an analysis-framework list (affinity mapping, impact/effort matrix, JTBD). Purely informational; it asks nothing and checks nothing.
- **ux-copy**: writes or reviews microcopy against five stated principles ("Clear," "Concise," "Consistent," "Useful," "Human") and worked patterns for CTAs, error messages ("What happened + Why + How to fix"), empty states, and confirmation dialogs ("Label buttons with the action: 'Delete files' / 'Keep files' not 'OK' / 'Cancel'"). Good, concrete prose guidance; still graded only by the model's own judgment of its own output, with no lint rule for banned words or required structure.

Across all seven, the only thing that is ever actually executed by a machine is whatever the connected MCP server does (e.g. Figma returning real measurements). Everything else — severity labels, scores out of 100, contrast numbers without a connector, "issues found: X" counts — is the model asserting a number inside a template.

## 5. Adopt / Reject / Open

All of the following are proposals only. Nothing in this repository has been changed to act on them.

- **Adopt (proposal) — UX copy skill.** CGSpec has no skill for microcopy, error messages, or empty-state text, and the plugin's five principles ("Clear, Concise, Consistent, Useful, Human") plus its error-message structure ("What happened + Why + How to fix") are concrete and reusable. Target: a new `skills/cgspec-ux-copy/SKILL.md`, written in CGSpec's own voice (no severity emojis, no invented score), wired as a sub-step of method section 6 rather than a standalone command. Not yet approved.
- **Adopt (proposal) — connector-placeholder wording for optional integrations.** The `~~category` placeholder convention (`CONNECTORS.md`) is a clean way to document "any tool in this category works, here is what we pre-wired" without hardcoding a vendor. If CGSpec ever documents optional MCP integrations (e.g. an issue tracker for `memlog.py` entries), reuse this exact pattern in a new `docs/_cgspec/CONNECTORS.md`-equivalent rather than inventing another format. Target: none yet — only relevant if/when CGSpec adds its first optional external connector. Not yet approved.
- **Reject — the design-system "Score: X/100" and the per-finding severity emoji tables.** Both present an ungrounded number or a traffic-light icon as if it were measured. CGSpec's rule in method section 7 ("Never 'zero defects': the claim is always 'these checks passed at this revision; these were not run'") already prohibits this kind of unearned precision; adopting the plugin's scoring format would be a regression.
- **Reject — treating "skill" and "slash command" as the same artifact.** The plugin's `SKILL.md` files are written entirely as command bodies (`/design-critique $ARGUMENTS`). CGSpec's skills (e.g. `skills/cgspec-ui-ux/SKILL.md`) are read by the agent as instructions during ordinary work, not just when explicitly invoked by name; collapsing the two would narrow when the guidance actually gets read.
- **Open — research-synthesis / user-research gap.** CGSpec has a market-research gate before design (section 1) but nothing that helps synthesize interviews, usability tests, or survey data once a project already has users. Whether this belongs inside `skills/cgspec-ui-ux/SKILL.md` layer 0 ("References") or as its own skill is an open design question, not resolved here.
